# Obsidian Vault Schema Refactor 产品规格

## 1. 文档状态

- 产品状态：**Go，进入 MVP 实现准备**。
- MVP 主题：Frontmatter 属性重命名及 Bases 引用同步修复。
- 平台：Desktop 为 MVP 完整支持平台；Mobile 首发仅开放 Doctor、扫描和 Review，写入默认关闭。
- 数据边界：仅操作当前 Vault 内文件和插件自己的本地数据。
- 网络边界：核心功能不发起网络请求。

## 2. 一句话定位

像 IDE 重命名代码符号一样重命名 Obsidian 属性：先找到全部定义和引用，展示影响与 Diff，再以可回滚事务同步修改 Markdown 和 Bases。

## 3. 背景

Obsidian 的属性是松散存储在 Markdown Frontmatter 中的键。Bases 又会在 filters、formulas、order、sort、groupBy 和 summaries 中引用这些键。用户在 Properties View 或批处理插件中重命名属性时，通常只改了 Markdown 数据，没有同步迁移 `.base` 引用。

结果不是总会出现明显错误。更危险的情况是：

- Base 正常打开，但返回空结果。
- 某个 formula 继续读取不存在的旧属性并产生空值。
- sort 或 groupBy 指向失效列，视图行为悄悄改变。
- 新旧属性同时存在，用户误以为迁移已经完成。
- 文件夹或笔记改名后，写死在 filter 中的路径仍指向旧实体。

这是典型的引用完整性问题。现有插件大多能修改属性数据，却不维护使用这些数据的声明式配置。

## 4. 已验证的需求

主要需求信号：

- Forum `104914`：属性重命名或删除后应更新所有受影响 Bases；持续活跃至 2026-07。
- Forum `115127`：公式中的属性引用不会随属性重命名。
- Forum `110831`：文件夹改名后 Base 仍引用旧路径。
- Forum `108976`：笔记/文件夹重命名后动态过滤条件失效。

竞品源码核对表明，Bases Toolbox、Frontmatter Operator、Bulk Properties、Forge、Fileclass 和 Formula Forge 均未完成“属性数据 + 全部 `.base` 引用”的统一、安全迁移。详见 [competitive-audit.md](./competitive-audit.md)。

## 5. 产品目标

### 5.1 MVP 目标

1. 让用户在一次明确操作中安全重命名一个 Frontmatter 属性。
2. 找出该属性在 Markdown Frontmatter 和所有 `.base` 结构中的引用。
3. 将确定性修改组成一个不可变计划，供用户审阅。
4. 以全有或全无的方式应用计划；失败时恢复原文件。
5. 支持事后撤销，并防止覆盖用户后续编辑。
6. 提供只读 Doctor，发现已失效的属性引用和 schema drift。

### 5.2 长期目标

- 支持属性删除、合并、拆分和类型迁移。
- 支持 formula 名称、文件夹和笔记路径重构。
- 为模板和静态 Dataview DQL 提供可确认的引用迁移。
- 提供机器可读审计报告，便于用户自己的 Git/CI 工作流使用。

## 6. 非目标

MVP 明确不做：

- 不替代 Obsidian Properties View、Bases 或通用 Frontmatter 编辑器。
- 不批量修改属性值；只迁移属性键和它的引用。
- 不执行 DataviewJS、Templater JavaScript 或任意用户代码。
- 不用文本全局替换修改普通正文、代码块或插件配置。
- 不承诺解释或运行 Base 查询结果。
- 不自动修复低置信引用。
- 不监听到属性变化后立即静默改写全 Vault。
- 不需要或内置 LLM。
- 不提供云同步、托管、账号或团队服务。

## 7. 目标用户

### 7.1 主要用户

- 使用 Bases 管理项目、任务、书籍、客户或研究对象的中高级 Obsidian 用户。
- Vault 中有大量 Properties，希望整理历史字段的人。
- 使用 Git 管理 Vault、重视可预览和可撤销变更的人。
- 维护模板或共享 Vault schema 的用户。

### 7.2 次要用户

- 插件作者和模板作者，需要审计样例 Vault 的 Base 引用完整性。
- 从 Dataview/Metadata Menu 迁移到 Bases 的用户。

### 7.3 不优先服务

- 完全不使用 Properties 或 Bases 的用户。
- 只需修改一两篇笔记且不存在引用的用户。

## 8. 核心概念

### 8.1 属性定义

Markdown Frontmatter 中实际存在的键值，例如：

```yaml
status: active
```

其中 `status` 是属性定义/实例。一个属性可以出现在多篇笔记中。

### 8.2 属性引用

`.base` 中用于读取、过滤、排序、分组或展示某属性的结构，例如：

- `note.status`
- 在上下文允许时使用的裸标识符 `status`
- View `order` 中的 `note.status`
- filter 表达式中的 `status == "active"`

### 8.3 Finding

只读扫描发现的一个事实或风险。Finding 不等于自动修改，例如“公式中出现无法确定语义的裸标识符”。

### 8.4 Change Plan

扫描某一时刻生成的不可变修改计划，包含源文件指纹、每项修改、冲突、排除项和预期结果。Plan 本身不写文件。

### 8.5 Transaction

一次应用 Change Plan 的完整操作。要么所有目标文件成功写入并通过校验，要么恢复到操作前状态。

### 8.6 Doctor

使用同一扫描与引用索引执行的只读健康检查。Doctor 只报告，不默认修改。

## 9. MVP 用户故事

### 9.1 重命名属性

作为使用 Bases 的用户，我希望把 `project-status` 改为 `status`，并同步更新所有笔记和 Bases，这样视图不会静默失效。

### 9.2 预览影响

作为谨慎的用户，我希望在修改前看到涉及多少文件、哪些引用会被替换、是否存在目标属性冲突，并能打开逐文件 Diff。

### 9.3 排除文件

作为维护混合用途 Vault 的用户，我希望从本次计划中排除某个 Base 或 Markdown 文件，并明确知道排除会留下哪些旧引用。

### 9.4 失败回滚

作为依赖大量自动化的用户，我希望某个文件写入失败时，已经写入的文件自动恢复，不留下半迁移状态。

### 9.5 撤销

作为用户，我希望在重构后发现问题时一键撤销；如果相关文件后来被修改，插件应提示冲突而不是覆盖新内容。

### 9.6 审计

作为用户，我希望 Doctor 告诉我哪些 Base 仍引用不存在的属性，并指出具体 Base、View 和字段位置。

## 10. 信息架构

插件提供一个主视图，包含两个标签页：

- **Refactor**：创建和执行属性重命名计划。
- **Doctor**：查看 Vault 范围的引用健康问题。

设置页仅包含持久偏好，不承载主要操作。

### 10.1 Refactor 页

固定流程：

```text
Configure -> Scan -> Review -> Confirm -> Apply -> Verify
```

用户不能跳过 Review 和 Confirm。

### 10.2 Doctor 页

```text
Scan -> Findings -> Inspect -> Create refactor plan / Export report
```

## 11. 完整重构流程

### 11.1 Step 1：配置

字段：

- `Old property`：从 Vault 已知属性中选择；允许键盘输入。
- `New property`：必填文本，实时校验。
- `Scope`：MVP 固定为整个 Vault，界面显示但不提供其他选项，避免用户误以为局部改名能保持 schema 一致。
- `Conflict policy`：当同一文件已存在目标属性时的处理策略。

配置校验：

- 旧名不能为空。
- 新名不能为空。
- 旧名和新名不能完全相同。
- 新名必须是可安全序列化的 YAML 字符串键。
- 默认拒绝包含换行、控制字符、前后空白的名称。
- 大小写变化视为有效迁移，例如 `Status -> status`。
- 若旧属性不存在于任何 Markdown，但存在于 `.base` 引用中，允许进入“只修复引用”流程，并明确标记。
- 若旧属性既没有定义也没有引用，禁止继续。

### 11.2 Step 2：扫描

扫描对象：

- 所有 `.md` 文件的 Frontmatter。
- 所有 `.base` 文件。
- 插件自己的历史记录不作为源数据扫描。

进度显示：

- 已处理文件数 / 总文件数。
- 已发现定义数、确定性引用数、需人工检查数和错误数。
- 用户可取消；取消不会写入任何文件。

扫描完成后生成 Change Plan。若扫描期间文件发生变化，在进入 Review 前重新读取受影响文件；无法稳定读取时阻止创建计划。

### 11.3 Step 3：审阅

顶部摘要：

- 将修改的 Markdown 文件数。
- 将修改的 Base 文件数。
- 属性实例数量。
- 确定性引用数量。
- 冲突数量。
- 警告和阻断项数量。

文件列表支持：

- 按文件类型、修改类型、严重程度筛选。
- 展开查看修改原因和结构路径。
- 打开并排 Diff。
- 排除单个文件。
- 从 Obsidian 中打开源文件。

每个修改必须显示原因，例如：

```text
Projects.base > views[0] "Active" > filters.and[1]
note.project-status -> note.status
```

低置信 finding 不可选中，也不能通过批量全选或逐项确认进入写入计划；MVP 只报告。未来若要支持人工确认写入，必须作为新需求重新定义验证和撤销规则。

### 11.4 Step 4：冲突处理

当同一 Markdown 文件同时存在旧属性和新属性时，定义为值冲突。MVP 提供以下策略：

- **Block and decide per file（默认）**：逐文件选择，最安全。
- **Keep target**：保留新属性值，删除旧属性。
- **Keep source**：用旧属性值覆盖新属性，再删除旧属性。
- **Merge lists**：仅当两者均为数组时可用；保持目标列表顺序，追加源列表中深度相等去重后的值。

MVP 不自动合并 scalar、object 与 array，不做字符串拼接。类型不兼容时只能 Keep target、Keep source 或排除文件。

大小写冲突按同样规则处理。YAML parser 若保留了两个仅大小写不同的键，视为两个独立键，不静默合并。

若 `.base` 的 `properties` 配置同时存在 `note.<old>` 和 `note.<new>`，这是 Base 配置冲突。MVP 只允许逐文件选择 **Keep target** 或 **Keep source**；不合并两个任意配置对象。未选择时该计划为 Blocker。filters、formulas、summaries、order、sort 和 groupBy 中的目标引用不是值容器，不产生此类冲突。

### 11.5 Step 5：确认

确认弹窗必须显示：

- 修改文件总数。
- 排除文件数和因此保留的旧引用数。
- 所选冲突策略。
- 将创建本地快照。
- 操作期间不要在外部编辑这些文件的提示。

存在以下情况时禁止确认：

- 未处理的阻断冲突。
- 无法解析的目标 `.base` 文件且其中可能包含旧属性文本。
- 计划创建后目标文件已变化。
- 快照目录不可写。
- 没有任何实际修改。

### 11.6 Step 6：应用

应用期间：

- UI 锁定当前计划，显示阶段和文件进度。
- 不允许关闭操作弹窗后让写入静默继续；关闭行为需二次确认。
- 插件先创建全部快照，再开始写源文件。
- 每写一个文件立即重新读取并验证目标字节。
- 任一写入或验证失败，停止后续写入并回滚已写文件。

### 11.7 Step 7：验证

成功写入后自动重新扫描：

- 所有计划内旧属性定义均已移除。
- 所有计划内高置信 `.base` 旧引用均已移除。
- 新属性实例数量符合预期。
- 所有修改后的 YAML 和 `.base` 可重新解析。
- 用户排除项和低置信项单独列出，不把它们算作失败。

结果状态：

- `Completed`：写入和验证均成功。
- `Completed with warnings`：确定性修改完成，但存在用户排除或低置信残留。
- `Rolled back`：写入失败，所有已写文件恢复成功。
- `Rollback incomplete`：至少一个文件未能恢复；必须列出文件并保留快照。这是最高严重度状态。

## 12. 引用处理规则

### 12.1 自动修改范围

MVP 自动处理：

- Markdown Frontmatter 的顶层旧键。
- `.base` 顶层 filters。
- `.base` 每个 View 的 filters。
- `.base` formulas 和 summaries 的表达式。
- View order、sort 和 groupBy 中明确表示 note property 的字段。
- properties 配置表中以属性 ID 为键的配置。

最终实现以 Obsidian 当前公开 `BasesConfigFile` 类型和兼容性样本为准。遇到未知字段时保持原值并报告，不删除。

### 12.2 不自动修改

- Markdown 正文。
- 普通代码块、DataviewJS、Templater 脚本。
- 字符串字面量中的同名文本。
- URL、文件名或标签中碰巧相同的文本。
- `.obsidian` 下其他插件配置。
- 无法解析的 `.base` 文件。

### 12.3 置信等级

- `Exact`：结构位置和语法均证明它是属性引用，可自动修改。
- `Probable`：上下文很可能是属性引用，但缺少公开 parser 保证；只报告。
- `Text match`：只是文本命中；只用于提醒，不进入默认结果。

Review 默认只展示 Exact 和 Probable；Text match 可通过开关查看。

## 13. Doctor 需求

### 13.1 MVP findings

- `MISSING_PROPERTY`：Base 引用的 note property 在 Vault 中没有任何实例。
- `MISSING_FORMULA`：View 引用不存在的 formula。
- `UNUSED_FORMULA`：formula 已定义但没有 View 使用。
- `CASE_DRIFT`：存在仅大小写不同的属性名。
- `TYPE_DRIFT`：同一属性存在明显不兼容类型。
- `UNPARSEABLE_BASE`：`.base` 无法解析。
- `UNKNOWN_BASE_SHAPE`：出现插件无法安全理解的配置形状。

### 13.2 Finding 展示

每项包含：

- Doctor 严重程度：Error、Warning、Info。
- 规则 ID 和短标题。
- 文件路径及 View 名称。
- 结构路径和遮盖后的片段。
- 为什么被判定为问题。
- 可执行动作：创建重构计划、打开文件、忽略本次、导出报告。

MVP 不提供永久忽略规则，避免早期规则不成熟时沉积不可见配置。

### 13.3 严重程度判定

同一个事实在 Doctor 和 Refactor 中可能有不同处置，但规则必须固定：

| Finding | Doctor 严重程度 | 创建当前重构计划时的处置 |
|---|---|---|
| `MISSING_PROPERTY` | Warning | 不阻断；可直接创建对应属性重构计划 |
| `MISSING_FORMULA` | Error | 与属性重命名无关时不阻断 |
| `UNUSED_FORMULA` | Info | 不阻断 |
| `CASE_DRIFT` | Warning | 与旧名或新名冲突时 Blocker，否则不阻断 |
| `TYPE_DRIFT` | Warning | 仅影响 Merge lists 可用性；类型不兼容时 Blocker |
| `UNPARSEABLE_BASE` | Error | 若文件原文可能包含旧属性，则 Blocker；否则不进入写入计划 |
| `UNKNOWN_BASE_SHAPE` | Warning | 若未知节点位于已知引用字段且可能包含旧属性，则 Blocker；否则只报告 |

`Blocker` 是计划状态，不是 Doctor finding 的严重程度。它表示当前计划在用户解决、排除或重新扫描前不能执行。

### 13.4 报告

可导出：

- Markdown：供人阅读。
- JSON：包含版本、扫描时间、Vault 相对路径、规则 ID、位置、严重程度和指纹，不包含 Vault 绝对路径。

报告默认不包含笔记正文或属性值。

## 14. 撤销与历史

### 14.1 历史记录

每次 Transaction 保存：

- 事务 ID、时间、插件版本和 Obsidian 版本。
- 旧名、新名、冲突决策和排除项。
- 修改文件相对路径。
- 修改前和修改后的内容哈希。
- 快照文件位置和状态。
- 应用与验证结果。

不记录 Vault 之外路径，不上传数据。

### 14.2 撤销规则

- 只有当前文件哈希仍等于事务记录的 `afterHash` 时才自动恢复。
- 文件在事务后被编辑时标记 `DIVERGED`，默认跳过，绝不覆盖。
- 用户可查看三方状态：重构前快照、重构后版本、当前版本；MVP 不提供三方合并。
- 撤销本身生成新的审计事件，但不删除原事务。
- 快照保留数量可配置，默认最近 20 次；清理前不得删除仍处于 Rollback incomplete 的事务。

## 15. 设置

MVP 设置项：

- 快照保留事务数：默认 20，范围 1-100。
- Doctor 是否在插件启动后延迟扫描：默认关闭。
- 是否在扫描结果中显示 Text match：默认关闭。
- 大 Vault 扫描并发度：自动；仅提供“低资源模式”开关。
- JSON 报告是否包含属性值类型统计：默认开启，不包含值本身。

不提供“跳过确认”“自动修复全部”等危险设置。

## 16. 状态和错误文案原则

- 区分“没有匹配”与“扫描失败”。
- 错误必须包含可行动信息：哪个文件、哪个阶段、数据是否已恢复。
- 不使用“完全安全”“零风险”等承诺。
- 修改数量使用实际文件和引用计数，不使用模糊文案。
- 任何回滚不完整必须持续可见，直到用户处理或确认知悉。

## 17. 可访问性与移动端

- 所有操作可用键盘完成。
- 颜色不是严重程度的唯一表达方式，同时使用图标和文本。
- Diff 在窄屏改为上下布局，不强制并排。
- 表格在移动端使用列表，不横向挤压关键文本。
- 长属性名和路径必须换行或中部省略，并可完整查看。
- 扫描和 Doctor 在应用切后台时可取消或安全暂停，不得继续无提示写入。
- Mobile 首发不执行源文件写入、自动回滚或 Undo；相关入口显示为只读，并明确说明可在 Desktop 完成操作。
- 后续开放 Mobile 写入的门槛是：Adapter 路径、快照持久化、后台中断、崩溃恢复和 10k 文件性能测试全部通过，且无 P0/P1。

## 18. 性能目标

以 10,000 篇 Markdown、200 个 `.base`、Frontmatter 总量 50 MB 的 Vault 为基准：

- 首次只读扫描目标：桌面端 10 秒内完成，P95 不超过 20 秒。
- 已有索引后的重复扫描目标：2 秒内完成未变化部分检查。
- 扫描过程不阻塞编辑器连续 100 ms 以上。
- Change Plan 生成后内存目标低于 200 MB，不复制无关正文。
- 应用时间由文件系统决定，但必须持续展示进度。

这些是发布目标，不是对所有设备的硬承诺。测试方法见 [test-plan.md](./test-plan.md)。

## 19. 隐私和安全

- 默认不联网，代码中不引入遥测 SDK。
- 扫描结果和快照只存放在插件数据目录。
- UI 和日志不输出完整属性值。
- 错误日志默认只含相对路径、规则 ID 和异常类型。
- 快照属于敏感 Vault 数据；设置页必须说明其位置、保留策略和清理方式。
- 删除快照使用 Obsidian Adapter 的明确文件列表，不递归删除未验证目录。

## 20. 成功指标

验证阶段：

- 20 个真实或脱敏复杂 Vault 中，至少 10 个发现用户认可的失效引用。
- Exact finding precision >= 99%。
- 自动重构后的漏修率 <= 1%，且所有漏修均作为 Probable/Text match 可见。
- 事务成功时零半迁移；故障注入时 100% 触发回滚。
- 测试用户无需阅读技术文档即可完成一次预览和重构。

发布后可在不使用遥测的前提下，通过用户主动提交的 issue/调查收集：

- 成功重构规模。
- 误报和漏报样本。
- 回滚触发原因。
- 最常见的后续重构类型需求。

## 21. MVP 验收标准

### 功能

- 可选择已知属性并输入新名称。
- 可扫描 Markdown 与 `.base` 并生成稳定计划。
- 可正确修改定义和所有支持的 Exact 引用。
- 可处理四种目标属性冲突决策。
- 可逐文件预览并排除。
- 可事务写入、验证、失败回滚和事后撤销。
- Doctor 可输出七类 MVP findings 和 Markdown/JSON 报告。

### 安全

- 未确认前零源文件写入。
- 计划过期时禁止应用。
- 不自动修改低置信引用和普通正文。
- 回滚不完整时保留全部快照和明确警报。

### 兼容

- 修改后的 Markdown Frontmatter 可被 Obsidian 正常读取。
- 修改后的 `.base` 可被目标最低 Obsidian 版本正常打开。
- 不依赖其他社区插件。
- 核心流程不依赖未公开 API。
- Desktop 在声明的最低 Obsidian 版本上支持完整流程；Mobile 首发只承诺只读流程。

### 质量

- 单元、契约、集成、端到端和故障注入测试通过。
- 性能基准达到第 18 节目标或有明确、可接受的偏差记录。
- 安装、升级、卸载不修改用户源文件。

## 22. 后续版本决策门槛

### 属性删除/合并

只有 MVP 的引用识别 precision 达标后再做，因为删除比重命名更难恢复。

### 文件夹和笔记重构

需先核对 Obsidian `FileManager.renameFile` 已自动覆盖的链接范围，只补 `.base` 等未覆盖部分，避免重复改写。

### Dataview 与模板

必须按语言建立 parser/grammar 或限定为可证明的静态语法；不得用全局正则替换冒充重构。

### 自然语言入口

只有 Doctor 能确定性校验候选结果后再考虑；模型只能提出计划，不能直接写文件。
